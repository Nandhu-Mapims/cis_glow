## 1. Module overview

**Purpose.** The Fees module runs the dental college's fee lifecycle: master-data setup (account
heads, fee types, banks, fines, course-wise fee amounts, scholarships), day-to-day fee collection
at the front desk, a two-person approve workflow for slips generated by non-cashier staff, a
two-person delete-request/delete-approve workflow for reversing posted receipts, collection/
delete/dashboard reporting, and parent communication (pending-fee SMS and printable pending-fee
reminder letters).

**Primary actors.**

| Actor | What they do here |
|---|---|
| Accounts/cashier staff | Fee Collection (`/fees/collection`), Approved Slips reprint/delete, Student Fee History reprint |
| Front-office/other staff (non-cashier) | Generate pending slips via legacy `student_fee_add_new.php` flow, land in Pending Slips (`/fees/slips/pending`) awaiting approval |
| Accounts supervisor / approver | Approve Fee Slip (`/fees/slips/:groupId/approve`), Fee Delete Approve (`/fees/delete/approve`) |
| Admin / setup staff | Fee Setup hub screens (account heads, types, banks, fines, amounts, scholarship, DME, ACMEC) |
| Management / accounts head | Fee Dashboard (`/fees/dashboard`), Collection Report, Delete Report |
| Any staff with `fees` menu access | Pending SMS, Pending Letter, ACMEC Scholarship Entry |
| `menuAuthForModule('fees')` / `accessType === 'Global'` | Gate on every route in `server/src/routes/fees.js:36` |

## 3. Pixel-level flow per screen

### 3.1 Fee Collection — `/fees/collection` (`FeeCollectionPanel.jsx`, legacy `student_fee_slip_new.php`)

**Search card** (`cis-fee-collection-search`):
- Label `Roll No` + red `*` (`<span className="text-danger">*</span>`), input `#fee-collection-roll`, `maxLength={10}`, forced uppercase via `style={{ textTransform: 'uppercase' }}` and `onChange` uppercasing.
- Button `Go` (label switches to `Loading…` while `generating`).
- Also pre-fills `registerNo` from `?registerNo=` query param (used by "Collect fees" deep links from History/Pending Slips).

Submit calls `POST /api/fees/collection/sheet` with `{ registerNo, paidDate }` →
`loadStudentFeeCollectionSheet` → `loadCollectionSheet` (`feeSlipCollectionLoad.js`). Client-side
validation error: `Register number is required` if empty.

**Response renders:**
- Hero card: student name (`cis-fee-student-name`), `{registerNo} | {courseLabel}`, 100×120 photo if present.
- Tabbed sheet, one tab per `feeTypeTabs` (fee_type_master rows), tab label = `fee_type_name`.
- Per tab table columns: checkbox header `Paid` (select-all for that tab, disabled if no pending rows), `Type`, `Fee` (right-aligned, strikes through scholarship-deducted amount via `<del>`), `Balance` (badge if > 0, else muted `0`), `Amount` (editable input, disabled `—` once `status === 'paid'`).
- Section rows group by `sectionLabel` = `"{Year} Year | {academicYear} | {academicBatch}"`.
- Footer row: `Balance Amount` = sum of pending row balances.
- Per-tab summary panel: `Type total` (readonly), `Fee` (readonly), `Fine` (readonly, only the type with max fine gets it applied per `computeFeeCollectionTotals`), `Concession` (editable amount input), `Concession details` (editable text, only shown when concession amount > 0).
- Bank radios (`pay_bank`): `Central Bank` (`cbi`), `Axis Bank` (`axis`), `State Bank` (`sbi`) — hardcoded `BANK_OPTIONS` in the panel, not server-driven.
- Button `Generate Slip` — disabled while `saving`, or `!hasPending`, or `selectedCount === 0`, or `totals.grandTotal <= 0`; label becomes `Generating…` while busy. Helper text below: `Select fee lines and enter amounts to generate a slip.` shown whenever nothing is selected/zero total but pending rows exist.
- Sidebar "Payment Summary": `Total balance due`, `Selected balance`, `Collecting now` (readonly, `totals.grandTotal`), `Date` input (`type=date`, id `fee-collection-date`) with hint `Change date and click Go to recalculate fines.`, and `{n} line(s) selected` when applicable.

**Validation before submit** (`generateSlip` in `FeeCollectionPanel.jsx`): `Load a student fee sheet first` if no `meta`/no pending; `Select at least one fee line` if `selectedCount === 0`; `Total amount must be greater than zero` if `grandTotal <= 0`.

**Save call:** `PUT /api/fees/collection/sheet` with `{ meta, entries, feeTypes, paidDate, payBank, totals }` (totals built via `totalsPayload`) → `saveStudentFeeSlip` → `saveCollectionSlip` (`feeSlipCollectionSave.js`). Server requires `selected.length > 0` else `{ success:false, error:'Select at least one fee line' }` (400). On success returns `{ success:true, message:'Fee slip generated', groupId, receiptHtml }` — a triplicate bank-slip HTML (`COLLEGE COPY / BANK COPY / REMITTER'S COPY / REMITTER'S COPY`) built by `wrapSlipCopies`. **This flow writes to `fee_slip_tb` only (pending, `f_status=0`)** — the actual `student_fee` insert happens later at the approval step (`saveApprovalSlip`), i.e. this is the two-person delete-request-analogue on the collection side: cashiers with slip privileges post here, someone approves the slip before it lands in `student_fee`.
- Success shows `Bank slip preview` card with `Print Slip` button (`printFeeSlip`, `client/src/utils/printReport.js`).

### 3.3 Approve Fee Slip — `/fees/slips/:groupId/approve` (`FeeSlipApprove.jsx`, legacy `student_fee_add_new.php`)

- On mount: `POST /api/fees/slips/approve/load` `{ groupId }` → `loadFeeSlipApproval` → `loadApprovalSheet`.
- Header: slip group id shown as `Slip group: {groupId}` (monospace); hero card shows student name, register no, badge `Awaiting approval`.
- Card `Slip lines to post to student_fee`: `Paid date` input; buttons `Save` (disabled while `saving`, label `Saving...`) and `Save & Print` (secondary style).
- `FeePaymentModeFields` (`client/src/components/FeePaymentModeFields.jsx`) — payment-mode selector: `Payment mode` select (`Bank`, `RTGS/NEFT`, `Cash`, `Cheque`, `D.D`). Conditional fields:
  - Bank/RTGS: `Transaction no.`, `Bank date (dd-mm-yyyy)`, `Amount`.
  - Cash: `₹2000 x`, `₹500 x`, `₹100 x`, `₹50 x`, `Other`.
  - Cheque/D.D: `Cheque no.`/`D.D no.`, `Date (dd-mm-yyyy)`, `Bank name`, `Amount`.
- Table: `Fee`, `Balance`, `Paid` per entry; footer `Total: {money}`.
- `approve(withPrint)` → `POST /api/fees/slips/approve` `{ groupId, meta, entries, feeTypes, paidDate, payment, submitAction: 'Submit'|'Submit_Print' }` → `saveApprovalSlip`. Validation: `groupId, meta and entries are required`; `No fee lines to approve` if nothing selected. Server inserts one `student_fee` row per selected line with `del=1`, generates a sequential `receipt_no` per fee type (`nextReceiptNo`, prefix = `fee_type_master.fee_id`), marks the label `- Part Payment` / `- Balance Amount` when partial. Marks `fee_slip_tb.f_status = 1` for the group. Returns `{ success, message: 'Approved and receipt generated' | 'Approved', receiptNos, receiptHtml? }`. On success, page auto-redirects to `/fees/slips/pending` after 2s.
- `Save & Print` renders a receipt card + `ReportPrintBar` labeled `Print Receipt`.

### 3.4 Approved Slips — `/fees/slips/approved` (`FeeApprovedSlips.jsx`, legacy `student_fee_delete.php`)

- Search card `Search posted slips`: `Register No` input, `Search` button, count text `{total} approved slip(s)`.
- `GET /api/fees/slips/approved?page=&search=` → `listApprovedFeeSlips` (`fee_slip_tb` where `del=1 AND f_status=1 AND group_id != '' AND id > 540`, `GROUP BY group_id`, paginated 20/page).
- `DataTable` columns: `Register No` (link), `Student`, `Slip ID` (monospace), `Paid Date`, `Bank`, `Receipts` (joined), `Approved` (by + at), `Amount`, `Status` (`Posted` badge), `Actions` (`Reprint`, `Delete`).
- `Reprint` → `POST /api/fees/receipts/reprint { groupId }` → `printReportHtml`.
- `Delete` opens `ConfirmModal` title `Delete approved slip?`, message `Delete approved slip {groupId}? This soft-deletes fee_slip_tb and student_fee rows.`, buttons `Delete slip` / `Cancel`. Confirm → `DELETE /api/fees/slips/approved/:groupId` → `deleteApprovedFeeSlip`: sets `del=0` on both `fee_slip_tb` (matching `group_id`) and `student_fee` (matching `slip_id`) — **this is a direct staff-initiated delete, distinct from the receipt Delete Request/Approve two-person workflow** (§3.9/3.10), used for slips that were never posted to the official receipt-delete ledger.
- Pagination footer: `Page {page} of {totalPages} ({total} total)`, `Previous`/`Next` buttons.

### 3.5 Fee Dashboard — `/fees/dashboard` (`FeeDashboard.jsx`, legacy `fee_dashboard_v2.php`)

- Filter card: `As on date` input (`type=date`, `max` today), button `Refresh` (`Loading…` while generating).
- Loads in 3 phases against `POST /api/fees/dashboard` with `{ attendanceDate, phase }`: `summary` (fast — collection stats), `table` (course-wise fee amount/paid/pending grid), `kpis` (per-year quick-summary KPI cards). Progressively injects the table HTML and KPI HTML into the summary HTML string (`injectSummaryTable`, `injectQuickSummary`) — dangerously-set-inner-HTML render (`fee-dashboard-root legacy-widget-root`).
- Client-side session cache: `sessionStorage['cis_fee_dashboard_v3']`, TTL 120s, keyed by ISO date — serves cached HTML while re-fetching in background if stale beyond that window; a refresh always forces a re-fetch (`forceRefresh: true`).
- Skeleton loading state while no HTML yet (`FeeDashboardSkeleton`), and an `Updating dashboard…` spinner overlay while refreshing on top of already-shown HTML.
- Drill-down: dashboard HTML wires up global `window.callFeeReport(course, ayear, atype, cyear, cdate, ctype, fcat, hostel, examination, stationary)` (called from inline `onclick` in the pending-cell table cells built server-side) → `POST /api/fees/dashboard/report` → opens a print window via `printReportHtml`.
- Server side `buildCourseSummaryTable` computes, per course × year: `Fee Amount` (sum `fee_name_master.fee_amount`), `Fee Paid` (sum `student_fee.fee_amount` up to the as-on date for that academic year), `Fee Pending` = `max(amount - paid, 0)` — clicking a pending cell triggers `callFeeReport(...)`.
- Quick Summary panel (right column) shows per-academic-year KPI cards: `Fee Amount`, `Fee Paid`, `Fee Unpaid`, `Scholarship`, `DME Tuition Fee`, `ACMEC Scholarship`, plus an `Overall unpaid` block: `College`, `Hostel`, `Exam`, `Stationary`, `Scholarship`, `DME`.

### 3.12 Pending SMS — `/fees/pending-sms` (`FeePendingSms.jsx`, legacy `fee_pending_sms.php`)

- Card `Class selection`: label `Classes`, `FeeMultiDropdown` (checkbox multi-select, grouped by course/batch label, placeholder `Select one or more classes`), button `Go` (disabled until at least one class selected, or while `busy`/`sending`).
- `GET /api/fees/pending-sms/classes` on mount populates class groups. `POST /api/fees/pending-sms/generate { selectedClasses }` on Go.
- Server (`generatePendingSms`): for each class key (`courseId___academicYear___currentYear___academicBatch`), pulls students with `mobile_no != '' AND father_mobile_1 != ''` and active enrollment (`releaving_date = '0000-00-00' OR releaving_date > today`), computes each student's pending fee sheet (`loadCollectionSheet` with `pendingOnly: true`), builds an SMS text: `Dear Parent, Your {son/daughter} {name}, Fee Pending details {feeLine: amount; ...; Total: N}.  If paid, please check with your student portal.-APDCH`.

## 4. Primary user stories

**US-1 — Collect a fee payment.**
As accounts staff, I want to look up a student by roll number on `/fees/collection`, select
outstanding fee lines, adjust amounts within balance limits, pick a bank, and click `Generate
Slip`, so that a bank-format triplicate receipt is produced and the amount is queued for
approval.
Acceptance: `Go` with empty roll shows `Register number is required`; loaded sheet groups fees
into type tabs; selecting a paid-off row is impossible (checkbox disabled); `Generate Slip`
disabled until at least one pending line is selected and `grandTotal > 0`; success shows
`receiptHtml` with a working `Print Slip` button.

**US-2 — Approve a slip generated by another staff member.**
As an accounts supervisor, I want to open `/fees/slips/pending`, click `Approve` on a slip, review
the lines and amounts, pick a payment mode, and `Save` (or `Save & Print`), so that the amount is
finally posted to `student_fee` with a real receipt number.
Acceptance: approving with no selected lines yields `No fee lines to approve`; a successful `Save
& Print` shows a printable receipt (`ReportPrintBar` labeled `Print Receipt`) and auto-navigates
back to the pending list after 2 seconds.

**US-3 — Look up a student's payment history and reprint a receipt.**
As accounts staff, I want to search `/fees/history` by register number and reprint any past
receipt, so that I can hand a duplicate slip to a parent.
Acceptance: searching an unknown roll shows the API error message; `Reprint` disables itself
(`Printing…`) while in flight and opens a print window on success.

**US-4 — Reverse a posted receipt via the two-person delete workflow.**
As accounts staff, I want to search a receipt on `/fees/delete/request`, submit a delete request
with remarks, so that a supervisor can review and approve it before the receipt actually
disappears from the ledger.
Acceptance: submitting when a pending request already exists for that receipt is rejected
server-side (`A pending delete request already exists for this receipt`); my own request list
shows a `Pending` badge until approved.

**US-5 — Approve a receipt deletion.**
As a supervisor, I want to review the pending-delete queue on `/fees/delete/approve`, inspect the
receipt detail, and confirm the delete, so that `student_fee` reflects the reversal and the
requester's status flips to `Deleted`.
Acceptance: `Delete Receipt` requires confirming through the modal (`Delete receipt {no} from
student_fee? This cannot be undone.`) before the DELETE mutation fires.

**US-6 — See the fee dashboard for a chosen as-on date.**
As management, I want `/fees/dashboard` to show today's/this-month's collection totals and a
course/year fee-amount/paid/pending grid, so that I can gauge collection health at a glance and
drill into any pending cell for the student-level list.
Acceptance: changing `As on date` and clicking `Refresh` re-fetches; clicking a pending amount
cell opens a print window with the drilled-down student list for that course/year/type.

**US-7 — Configure course-wise fee amounts.**
As setup staff, I want `/fees/setup/name` to let me pick a course batch, switch between year tabs,
and edit fee type/bank/quota/academic-type/caste/name/amount/scholarship/discount per row, so that
the collection screen calculates the right balances for each student.
Acceptance: rows already used in a posted collection are locked (amount/discount read-only, no
delete) so historical receipts stay reconcilable; `Save` requires a selected batch.

**US-8 — Generate and send pending-fee SMS to parents.**
As accounts/front-office staff, I want to select one or more classes on `/fees/pending-sms`,
`Go` to preview the message list, and `Send SMS` after confirming, so that parents of students
with outstanding fees get a reminder text.
Acceptance: `Go` disabled with no class selected; `Send SMS` requires the confirm-modal click;
result message is `{n} SMS Sent...`.

**US-9 — Generate and print pending-fee reminder letters.**
As front-office staff, I want to select classes on `/fees/pending-letter`, `Go` to build printable
letters, and `Print` them, so that students without an SMS-capable channel (or as a formal
document) still get an outstanding-fee notice with an official reference number.
Acceptance: only students with a pending balance and both `mobile_no` and `father_mobile_1`
populated are included; letters carry a unique ref `APDC&H/Fee-Rem/{academicYear}/FRL{registerNo}`.

**US-10 — Flip a student's scholarship/DME/ACMEC eligibility flags.**
As setup staff, I want `/fees/acmec-config` to let me search a student (by roll or by batch) and
toggle `Scholarship`, `First Graduate`, `ACMEC Scholarship` (with amount/approved), and record DME
tuition-fee receipt details, so that downstream scholarship/DME/ACMEC approval screens can find
and settle amounts for that student.
Acceptance: saving with a register number that collides with a different student id is rejected
(`Roll number already exists for another student`); unchecking `Scholarship` also clears caste
scholarship, first-graduate, and ACMEC-trust flags server-side.

## 5. Rare / edge-case user stories

**5.1 — Two-person delete-request vs delete-approve.**
As a compliance-minded accounts head, I want the receipt-deletion request and its approval to be
two distinct actions (`fee_delete_request.php` submit vs `fee_delete_approve.php` confirm) so no
single staff member can silently erase a receipt.
As implemented today, `submitFeeDeleteRequest` and `approveFeeDeleteRequest`
(`server/src/services/fees/feeDelete.js`) do **not** check that `req.user.memberId` on approval
differs from `created_by` on the request — the same logged-in account could, in principle,
request and then approve their own deletion in two separate calls. This is a gap worth flagging
for a stricter server-side check (compare `created_by` vs approving `memberId`) if segregation of
duties is a hard requirement.

**5.2 — Partial payment.**
As accounts staff, when a student pays less than the full balance on a fee line, I want the system
to record it as a partial payment and keep tracking the remaining balance, so the student can pay
the rest later.
`clampPayAmount` (`feeCollectionTotals.js`) clamps the entered amount to `[0, balanceAmount]`
client-side. `saveApprovalSlip` labels the receipt line `{feeName} - Part Payment` when
`paymentNo === 1` and `tfeeAmount > feeAmount`, and `{feeName} - Balance Amount` for any subsequent
partial payment (`paymentNo > 1`). Next time `/fees/collection` is loaded for that student, the
same fee row reappears with `balanceAmount = feeAmount - paidAmount` and `paymentNo` incremented.

**5.3 — Fee sheet for a student with a scholarship/concession applied.**
As accounts staff, when a student's fee line is marked `feeScholarArray`-eligible (a scholarly fee
label) and a `student_fee_scholarship`/`student_fee_dme`/`student_fee_acmec` amount exists for
their year/batch, I want the collection sheet to show the discounted amount automatically.
`loadCollectionSheet` (`feeSlipCollectionLoad.js`) deducts `scFeeAmount[year][classYear][batch]`
from `feeAmount` when the fee-name id is in `feeScholarArray`; the UI shows the original amount
struck through (`<del>{entry.scholarshipDeducted}</del>`) next to the discounted `Fee` cell
(`ScholarshipHint` in `FeeCollectionPanel.jsx`). If the ACMEC/DME/scholarship flag was never set
on the student's profile (§3.8/3.19-3.21), the discount never applies — this is the same gap the
ACMEC Scholarship Approved screen's empty-state message calls out directly (`none have ACMEC
Scholarship enabled on their profile ... Enable it under Fees → ACMEC Scholarship Entry`).

**5.4 — Sending SMS to a student with no registered mobile number.**
As accounts staff generating pending SMS, I expect students without a parent mobile on file to be
silently excluded rather than error out. `generatePendingSms` filters
`AND P.mobile_no != '' AND P.father_mobile_1 != ''` at the SQL level, so those students never
appear in the generated `rows` list — there is no separate warning surfaced for them individually,
only the aggregate empty-state message if the whole selection yields zero rows (`No pending fee
SMS found for the selected class(es)... some classes may have no enrolled students or no
outstanding fees.`). The pending-letter flow has the identical filter and a near-identical
messaging gap for individual missing-mobile students.

**5.5 — Generating a pending letter/SMS for a student with a zero balance (should be excluded).**
As accounts staff, I expect students who have fully paid should never receive a pending-fee
SMS/letter. `buildPendingText` (`feePendingSms.js`) filters entries to
`balanceAmount + feeFine > 0`, and if the resulting `pendingText` is empty, that student's row is
dropped (`if (!pendingText) return null;`) before being added to the SMS batch. Likewise
`buildPendingAmountHtml` (`feePendingLetter.js`) filters `entries.filter((entry) =>
Number(entry.balanceAmount || 0) > 0)` and returns `''` (skipping the letter) if nothing is
pending. So a zero-balance student is correctly excluded from both flows even if they are
technically enrolled in a selected class.

**5.6 — Concurrent fee collection by two staff for the same student.**
As accounts staff, if two cashiers simultaneously load the same student's fee sheet and both
submit a slip for the same fee line, I want to understand the actual behavior: `loadCollectionSheet`
computes balances read-only at load time with no row locking, and `saveCollectionSlip` /
`saveApprovalSlip` simply INSERT new `student_fee` rows keyed by a freshly generated
`receipt_no` — there is no optimistic-concurrency check against the balance computed at load time.
Two near-simultaneous submissions for the same fee line could both succeed, potentially
over-collecting (paying more than the outstanding balance) since balance is only recomputed on the
next full page load, not re-validated at save time. This is a known-risk gap worth flagging for a
future server-side re-check of remaining balance immediately before insert.

**5.7 — Permission denial.**
As a user without `fees` module menu access (and not `accessType === 'Global'`), every request
under `/api/fees/*` is rejected by `menuAuthForModule('fees')`
(`server/src/routes/fees.js:36`) before reaching any handler — consistent with `docs/auth-flow.md`
gate described in `CLAUDE.md`.

**5.8 — Empty datasets.**
Multiple screens have distinct, quoted empty-state copy rather than a blank page: Pending Slips
(`No pending slips found.` / `No pending slips for register {roll}.`), Approved Slips (`No approved
slips found.`), Collection Report (`No fee collection data for the selected filters.`), Delete
Report (`No deleted receipts for the selected period.`), Scholarship setup (`No scholarship
students found for this course, year, and class...`), DME setup (`No DME receipt rows found for
this course and year.`), ACMEC Approved setup (differentiates "0 enrolled" vs "enrolled but none
flagged").

**5.9 — Network/API failure.**
Every screen catches Axios errors and falls back to `err.response?.data?.message` with a generic
per-screen fallback (e.g. `Unable to load fee dashboard`, `Report failed`, `Submit failed`,
`Approve failed`) rendered in a Bootstrap `alert-danger` box — none of the fee screens leave the
user with an unstyled crash; failed loads reset dependent state (e.g. `FeeCollectionPanel.resetSheet()`
on load failure).

**5.10 — Duplicate/locked keys.**
`FeeNameSetup` rows already referenced by a posted `student_fee` row become `locked` (server marks
`locked: usageCount > 0` from `prisma.student_fee.count({ where: { fee_id: String(row.id) } })`) —
the UI disables editing amount/discount and hides the delete button for those rows, preventing a
setup edit from silently invalidating historical collection math. `ACMEC` config rejects saving a
`registerNo` that already belongs to a different `student_profile_tb.id`.

**5.11 — Zero dates.**
`formatDisplayDate` (`feeHelpers.js`) and the setup-specific date formatters treat any date string
starting with `'0000'` as empty (returns `''`), consistent with `CLAUDE.md`'s zero-date rule; fee
fine due-date SQL filters explicitly exclude zero dates
(`CAST(fee_due_date AS CHAR) NOT LIKE '0000-00-00%'` in `computeFine`).

**5.12 — Approved-slip delete vs receipt delete-request are two different soft-delete paths.**
Deleting from `/fees/slips/approved` (`deleteApprovedFeeSlip`) is a single-click staff action (no
second approver) that soft-deletes both `fee_slip_tb` and matching `student_fee` rows by
`slip_id`/`group_id`. Deleting a receipt through `/fees/delete/request` +
`/fees/delete/approve` requires two people and only touches `student_fee` by `receipt_no`. Staff
should understand these operate on different keys (`group_id` vs `receipt_no`) and neither
automatically triggers the other's audit trail (`fee_delete_tb` vs plain `log_tb` entries).

## 6. Future / predicted user stories

### Future (not implemented)

These are speculative extrapolations grounded in [../mobile.md](../mobile.md); none of the
following exists in the codebase today.

- **Mobile read-only fee balance/history view.** `mobile.md` §6 lists `Fees` under the mobile
  feature-mapping table with the note *"Read balance/history first; payment collection UI is a
  stretch goal (§8)"* and §9 Phase 1 explicitly scopes "Fees (view)" into the read-only core. A
  future mobile app screen would likely reuse `GET /api/fees/students/:registerNo/history` (same
  endpoint `StudentFeeHistory.jsx` calls today) rendered as a native list instead of Bootstrap
  cards, with `Print`/`Reprint` replaced by `expo-print` → `expo-sharing` per §7.1 of `mobile.md`.
  As a student or parent, I might want to open the app and see my/my child's current fee balance
  and past receipts without needing the desktop portal — but this is unbuilt and unconfirmed.

- **Fee payment gateway from mobile.** `mobile.md` §8 explicitly lists *"Fee payment gateway from
  mobile — if fees currently redirect to a bank gateway page in the web flow, confirm that flow is
  mobile-webview-safe... this *is* new backend surface — flag and scope separately, get sign-off
  before building."* This module's current collection flow (`/fees/collection`,
  `/fees/slips/*/approve`) is entirely staff-operated (cashier enters payment mode details
  manually — Bank/RTGS reference no, Cash denominations, Cheque/D.D details); there is no
  self-service online payment gateway integration anywhere in `server/src/services/fees/`. A
  future "pay your fee online" mobile/web self-service flow would require new backend surface
  (gateway integration, webhook/callback handling into `student_fee`) that does not exist and is
  explicitly flagged in `mobile.md` as unconfirmed and requiring sign-off — it must not be assumed
  or described as available.

- **Push notifications for fee due dates.** `mobile.md` §8 flags push notifications (including fee
  due reminders) as new backend surface requiring a new `server/src/services/push/` sender
  triggered from "existing circular/fee services" — today the only outbound parent communication
  channels for fees are the SMS batch (`/fees/pending-sms`) and the printed reminder letter
  (`/fees/pending-letter`), both staff-triggered, not automated or push-based. A plausible future
  story: "As a parent, I want a push notification a few days before my child's fee due date," but
  this depends on the Phase 4 push infrastructure `mobile.md` §9 defers pending explicit sign-off.

- **Self-attendance-style light-write parity for fees.** `mobile.md` §9 Phase 3 mentions "Light
  write" mobile capability generally (self-attendance marking, profile edits "allowed to the
  logged-in role") but does not name any fee-specific write action — collection, approval, and
  delete-request/approve are all described in `mobile.md` §6's Fees row as read-first with payment
  UI as only a stretch goal, so no mobile write capability for Fees should be assumed beyond
  reading balance/history.
