# 08 — Fees

## 1. Module recap

The Fees module runs the college's fee lifecycle: master-data setup (account heads, fee types,
banks, fine rules, course-wise fee amounts, scholarship/DME/ACMEC), day-to-day collection at the
front desk with a two-person slip-approve workflow, a separate two-person delete-request/
delete-approve workflow for reversing posted receipts, collection/delete/dashboard reporting, and
parent communication (pending-fee SMS and printable reminder letters). Full field-by-field detail
— every screen's inputs, validation messages, and save payloads — is documented in
[../user-stories/08-fees.md](../user-stories/08-fees.md); this file builds on that base and only
re-states what's needed to justify a UX call.

Two facts shape most of what follows:
- Money-handling screens (Collection, Slip Approve) are dense, single-purpose panels with real
  inline calculation feedback already (balance/fine/concession recompute live) — the control gaps
  here are mostly around bulk operations and confirmation safety, not missing search/select
  widgets.
- List/report screens (Pending Slips, Approved Slips) already use the shared `DataTable`
  component (search + sort + pagination built in); the setup screens (Fee Amounts, Fine Rules,
  Scholarship, DME, ACMEC) are flat editable grids with no search at all, which matters once a
  course batch has 100+ students.

## 3. Advanced feature gaps

1. **`FeeMultiDropdown` has no search and no bulk select-all/clear, despite `CheckListSelect` already providing both.** Pending SMS and Pending Letter's "Classes" picker is the module's only true multi-select-from-a-long-list control, and it's the one place search matters most — a college with dozens of course/year/batch combinations means scrolling a long ungrouped-within-group checkbox popover to find the right class. `CheckListSelect` (search appears automatically past 8 options, plus "Select all"/"Clear") is already built and used elsewhere in the app; swapping it in here is a direct, proven-elsewhere fix, not a new component to build.

2. **Fee Amounts' in-grid multi-selects (Academic Type, Scholarship Community) inherit the same no-search gap.** These are typically short lists (Regular/Additional/Break; a handful of caste categories) so search matters less, but the missing bulk select-all/clear still means an admin ticking "apply to every scholarship community" does it one checkbox at a time.

3. **Setup screens with per-student grids (Scholarship, DME, ACMEC Approved) have no in-grid search or sort**, unlike the list screens (Pending Slips, Approved Slips) which already get `DataTable`'s search-and-sort for free. A 100+ row scholarship-approval grid with no way to jump to a specific roll number is a real friction point for the exact kind of "review and approve amounts" workflow these screens exist for. Wiring these onto `DataTable` (or at minimum adding a client-side filter input) would bring them to parity with the list screens two clicks away in the same module.

4. **No confirm modal before `Save`/`Save & Print` on Approve Fee Slip**, even though this is the step that actually posts to `student_fee` with a real, sequential receipt number — the two delete flows (Approved Slips delete, Delete Approve) both get a `ConfirmModal`, but the money-posting action does not. This is an inconsistency within the module's own confirmation pattern, not a missing feature invented from nothing.

5. **No batch-approve on Pending Slips.** The list already has search + pagination via `DataTable`, but each row only offers a per-slip `Approve` link that navigates to a separate detail page. For an accounts supervisor clearing a backlog of same-payment-mode slips at day's end, there's no "select several, apply one payment mode, approve all" path — every slip requires a full page navigation.

## 4. User-experience suggestions

- **Bulk fee-sheet actions on Fee Collection.** The per-tab "select all pending" checkbox already exists — extend it with a cross-tab "select all pending fee lines across every tab" toggle, since a student with balances across multiple fee-type tabs currently requires switching tabs to select each one before `Generate Slip` becomes eligible. This reduces clicks for the common "pay everything owed" case without changing the underlying selection/validation logic.
- **Confirmation on Approve Fee Slip's Save/Save & Print.** Since this step is irreversible in the normal flow (receipt number generated, `f_status` flipped) and the module already has a `ConfirmModal` pattern used consistently for deletes, adding the same pattern here (`Post {n} fee line(s) totalling ₹{total} to student_fee?`) closes an inconsistency and protects against a supervisor clicking Save on the wrong slip.
- **Autosave draft receipts on Fee Collection.** The collection sheet supports live-editable amounts, concession, and bank selection before `Generate Slip` — if a cashier is interrupted mid-entry (a common front-desk scenario), there's currently no draft persistence; a debounced local-draft save (even just to `sessionStorage`, keyed by roll number) would let them resume without re-entering amounts.
- **Inline balance-due calculation feedback, extended.** The collection panel already does this well (footer `Balance Amount`, per-tab Fee/Fine/Concession totals, sidebar `Total balance due` / `Selected balance` / `Collecting now`) — the same live-recompute pattern would help on Fee Amounts setup (show a running "this changes N students' balances" hint when a locked-vs-unlocked amount is edited) and on Fine Rules (a preview of "3 fee types affected" as due-date/amount fields change), since both currently save blind with no preview of downstream impact.
- **A payment-mode toggle group on Approve Fee Slip.** `FeePaymentModeFields` already conditionally renders different field sets per mode via a `<select>`; converting the top-level mode picker itself from a dropdown to a segmented button/toggle group (Bank | RTGS/NEFT | Cash | Cheque | D.D) would make the five options visible at a glance and match how a cashier physically sorts payment types, rather than requiring a dropdown click to see what's available.
- **Receipt search/filter/export on Student Fee History.** Currently a single register-number lookup returns up to 500 receipt rows as stacked cards with per-receipt `Reprint` — for a student with a long payment history, a quick filter (by fee type, date range, or amount) and a bulk "export/print full history" action (beyond one-at-a-time reprint) would help both accounts staff handling a walk-in dispute and any future self-service history view (the mobile read-only history view mentioned as a future story in the user-stories doc would need the same underlying filter).
- **Confirmation on Delete Request submission.** Delete Request (3.9) currently submits straight from the `Remarks` textarea with no confirm step, even though it's the entry point into a formal audit-trailed deletion workflow — a lightweight confirm (`Send delete request for receipt {no}? A supervisor will review this.`) sets the right expectation without adding real friction, since the actual deletion still requires a second person's approval regardless.
- **Better empty states for "no dues"/no-data screens**, generalizing the module's best example (ACMEC Approved's differentiated "0 enrolled" vs "enrolled but not flagged" message with a direct link to the source screen). Scholarship Setup and DME Setup currently show flatter messages (`No scholarship students found for this course, year, and class...`, `No DME receipt rows found for this course and year.`) without the same "here's why, and here's where to fix it" link — bringing them up to ACMEC's standard would reduce support tickets asking "why is this empty" for what's usually a profile-flag issue, not a bug.
- **Search within Scholarship/DME/ACMEC Approved grids.** Once a course/year is loaded, a client-side roll-number/name filter (same substring pattern already in `DataTable`'s `searchable` prop) would let an approver jump to a specific student instead of scrolling a 100+-row flat grid — directly reusing a pattern the module already has, just not wired onto these three screens.
- **Real per-row send progress on Pending SMS.** The progress bar (`{current} of {total} SMS sent…`) currently animates cosmetically while the actual send is one batched server call — either make the server stream progress (SSE/polling) or simplify the UI to an honest "Sending…" spinner, since a fake progress bar that doesn't reflect real per-row completion can mislead staff into thinking they can identify which specific message failed mid-batch.

## 5. Quick wins vs. bigger investments

**Quick wins (small diff, immediate win):**
- Add a `ConfirmModal` to Approve Fee Slip's Save/Save & Print — the component and pattern already exist in this exact module (`ConfirmModal.jsx`, used on Approved Slips delete and Delete Approve).
- Add a `ConfirmModal` to Delete Request submission, matching the same pattern.
- Swap `FeeMultiDropdown` for `CheckListSelect` on Pending SMS and Pending Letter's class picker — direct component swap, no new UI to design, immediately gains search + select-all/clear.
- Bring Scholarship/DME/ACMEC Approved setup grids up to ACMEC's differentiated empty-state copy standard (message-only change, no new logic).
- Add a client-side search input above the Scholarship/DME/ACMEC Approved grids (a much smaller lift than a full `DataTable` migration — even an uncontrolled filter over the already-loaded rows helps).

**Bigger investments (needs design/product buy-in first):**
- Cross-tab "select all pending fee lines" on Fee Collection touches the selection-state model (`selectedCount`/`totals` logic in `FeeCollectionPanel.jsx` and `feeCollectionTotals.js`) and needs product sign-off on how cross-tab totals should read in the sidebar.
- Batch-approve on Pending Slips is a genuinely new workflow (multi-select rows + apply one payment mode across several slips) — needs a server endpoint that doesn't exist today (`saveApprovalSlip` currently operates on one `groupId` at a time) and a product decision on what happens when selected slips have differing totals/fee types.
- Autosave draft receipts on Fee Collection needs a decision on where drafts live (session-only vs a real server-side draft table) and how conflicting-draft recovery is presented to the cashier.
- Migrating Scholarship/DME/ACMEC Approved grids onto the shared `DataTable` component (rather than a lighter client-side filter) is a bigger refactor — these screens have inline-editable Amount cells per row, which `DataTable` doesn't natively support, so it would need either a `DataTable` enhancement or a custom editable-table wrapper.
- Real per-row SMS send progress requires backend streaming/polling support that doesn't exist in `sendPendingFeeSms` today (it's a single synchronous batched call) — a genuine backend change, not a frontend-only fix.
- A payment-mode toggle group redesign for Approve Fee Slip is a visual/interaction change worth a quick design pass (five options, several with very different conditional field sets) before implementation, even though the underlying state model wouldn't change.
